## 0. The 60-Second Version

1. **Your Docker host isn't alone.** It can connect to *other* Docker hosts — which is exactly what Kubernetes does inside a cluster.
2. **The container lifecycle has more states than you think:** created → running → paused → stopped/exited → removed. And `created` ≠ `running`.
3. **`docker ps` hides stopped containers. `docker ps -a` shows everything.** Half of all Docker confusion lives in that one flag.
4. **`start` vs `restart`:** `start` boots from a fresh PID 1; `restart` resumes from the state you stopped at. Both work after a stop.
5. **You can't `rm` a running container** — stop it first, or force it with `-f`.
6. **Forcing things leaves rubbish behind:** dangling images, unused containers, zombie processes. `docker system prune` is the broom.
7. **`docker exec -it <id> /bin/bash` drops you inside a container** — and it's a tiny Linux box in there.
8. **Multi-stage builds exist because `node_modules` is enormous.** Build in stage 1, copy only the output into stage 2. Two keywords do all the work: `AS builder` and `--from=builder`.

## 4. Docker Images — Immutability & the Blueprint

### 🧠 Immutability, via Java

> 🎤 *"Docker image is an **immutable** object. Immutability — do you know it in Java? It **will not be changed**."*

> 🎯 **Her question: why do we say a Docker image is immutable?**
>
> ```
> Dockerfile  →  docker build  →  IMAGE  →  docker run  →  CONTAINER
>                                    ↑
>                     you now edit your source code...
>                     ...and NOTHING changes in the running container
> ```
>
> ✅ **Because the image is a frozen snapshot.** *"You need to **rebuild** the image. If you rebuild it, then those new changes will reflect inside your container. That's why we call Docker images a read-only template and immutable."*

### 🧠 Blueprint, via architecture

> 🧠 **Picture this.** *"Do you know the blueprint of a building? While architects are designing a building, they create a blueprint. Maybe you've seen it in movies — there's a building, four or five architects with **yellow hats**, and they go 'okay, this will be the building.' They sketch it, they colour it, and they show it to the client. Like a **township** — they draw the whole township, colour it, and give it to the client: 'see, this is what we're going to build.'"*
>
> ✅ **A Docker image is that drawing.** It fully specifies the thing without being the thing.

### 🐍 The five manual steps → the five Dockerfile lines

She rebuilt the blueprint argument from scratch, this time with **Python**:

> 🎯 *"Imagine you have a server and you don't have Docker. You need to deploy a Python application. What do you do?"*

| # | On a bare Linux server, by hand | The Dockerfile line |
|---|---|---|
| 1 | install **Python** | `FROM python:3.11` |
| 2 | create the **Python environment** | *(the image is the environment)* |
| 3 | install all the **libraries** from `requirements.txt` | `RUN pip install -r requirements.txt` |
| 4 | **`git clone`** your code | `COPY . .` |
| 5 | **run** it — `python app.py` | `CMD ["python", "app.py"]` |

> ✅ *"The five things we need to run an application — five instructions — we just put in a Dockerfile. **That's why we call a Docker image the blueprint of your application.**"*
>
> ⚠️ And the same caveat as Class 6: *"Same commands, **but with Docker instructions**"* — `FROM`, `RUN`, `WORKDIR`, `COPY`, `EXPOSE`, `ENTRYPOINT`, `CMD`.

### 🎯 The "trigger point" per stack

She made the class name the start command for each stack — this is the `CMD`/`ENTRYPOINT` line:

| Stack | Trigger point |
|---|---|
| **Python** | `python app.py` |

| **Apache** | same idea (`httpd-foreground`) |

## 5. Container Lifecycle — The Full Hands-On

```
        Dockerfile
             │  docker build
             ▼
      ┌────────────┐
      │   IMAGE    │
      └────────────┘
             │  docker container create
             ▼
      ┌────────────┐        PID 1 exists, but NOT started
      │  CREATED   │
      └────────────┘
             │  docker start
             ▼
      ┌────────────┐ ◄────────── docker run  (create + start in one)
      │  RUNNING   │
      └────────────┘
        │        │  docker pause
        │        ▼
        │  ┌──────────┐   internal services frozen,
        │  │  PAUSED  │   container still "running"
        │  └──────────┘
        │  docker stop  →  graceful shutdown, state saved
        ▼
      ┌────────────────┐  ──── docker restart ──► resumes saved state
      │ STOPPED/EXITED │  ──── docker start ────► fresh from PID 1
      └────────────────┘
             │  docker rm
             ▼
      ┌────────────┐
      │  REMOVED   │
      └────────────┘
```

### The `created` state — a container that exists but has never run

She used a command you don't normally reach for, specifically to show the state:

```bash
docker container create --name mynginx nginx
```

> ✅ *"Container is created."* But `docker ps` shows nothing. `docker ps -a` shows it as **Created**.

> 🎤 **On PID 1:** *"Whenever you **create** a container, that means PID 1 is created **but not started yet**. When you execute `docker run`, it starts the initialisation process — the PID 1 service — and it goes into the **running** stage."*

### 😄 The 5-second container

She ran it and it died almost instantly:

> 😄 *"It stopped. Started and stopped in 5 seconds. I need to start it and you need to check it in 5 seconds."*
>
> ⚠️ **Why:** *"I did not add `-d`, `-it`, or even `-p`. If you want your container to **keep running**, you need to add an **entry point** inside your Dockerfile. I did not do anything — I just created it. So it will **create and it will die.**"*
>
> ✅ **Lesson:** a container without a long-running foreground process (PID 1) exits immediately. That's not a bug — it's the definition.

Then:

```bash
docker start mynginx     # created → running
docker ps                # ✅ now it shows up (not just ps -a)
```

### 🧪 The best experiment of the class: does closing the terminal kill it?

```bash
docker run --name mynginx nginx     # NO -d, so it runs in the FOREGROUND
```

**With no `-d`, you see all the container's logs streaming live.** Then:

| Action | What happens |
|---|---|
| **`Ctrl + C`** | ❌ **container STOPS** |
| **close the terminal window** | ✅ **container KEEPS RUNNING** — the class guessed wrong on this one |
| **reboot / shut down the laptop** | ❌ **container stops** |

> 🧪 **She had the class prove it:** *"Open **two** terminals. In one, run `docker run --name mynginx nginx`. Then close that terminal. In the second terminal, run `docker ps -a`. Are you able to see a running container or a stopped container?"* → **running.**

> ✅ **And the rule that follows:** *"If you run your container **without** detached mode, then if something happens inside your server or laptop, your container will be stopped. But in **detached** mode — whether you close it or not — until you shut down your laptop it will be up. **In real time we're not doing this on laptops, we're doing it on servers, and for that reason we have to use `-d` detach mode. Always. Always.**"*

> 💡 **Vocabulary history:** *"Previously when Docker was invented they called it **daemon mode**. But now, after maybe 10 or 20 years, they call it **detach mode**."*

### `docker logs` — seeing output from a detached container

> 🎤 *"The people who made it, they are not fools. If you're running the container in detached mode and you still want to see the logs — then this is the command."*

```bash

### ⏸️ Pause vs 🛑 Stop — a real distinction

| | **`docker pause`** | **`docker stop`** |
|---|---|---|
| Container still "running"? | ✅ **yes** | ❌ no |
| Internal services | **frozen** — *"not functioning as required"* | shut down |
| Data | **state saved** — *"no data will be leaked or vanished"* | *"please save your file, save your state, and then stop"* — a **graceful shutdown** |
| When you'd use it | *"suddenly you have a problem with resources — less memory, your laptop is lagging"* | you're done with it for now |

> ✅ **Both preserve your data.** The difference is whether the container is still *there*, holding its process, or shut down cleanly.

### 🎯 `start` vs `restart` — she made this a task

> 🧪 **The experiment she assigned:**
>
> ```bash
> docker run -d --name mynginx nginx
> docker stop mynginx
> docker restart mynginx     # does this work?
> docker stop mynginx
> docker start mynginx       # does THIS work?
> ```
>
> ✅ **Answer: both work.** But they do different things:

| | **`docker start`** | **`docker restart`** |
|---|---|---|
| Where it begins | **fresh from PID 1** | resumes **the state you left** |
| Use it when | you need to *"completely refresh your application"* | you just stopped it and want it back |
| Which is normal | less common | ⭐ *"If you stopped it, we use **restart**."* |

> 🧠 **Her analogy:** `docker start` is like a full power-cycle — everything from scratch. `docker restart` is picking up where you left off. *"When you're stopping your container, the daemon stores the state, saves your file data and volume — that's the graceful shutdown. Once you restart it, it restarts from the state you left."*

### ⚠️ You can't remove a running container

```bash
docker run -d --name nginx1 nginx
docker rm <container-id>          # ❌ ERROR
```

> 🎯 **Her framing:** *"I'm jumping from a running stage **directly** to the remove stage. Can you see the error? Either you need to **stop** it and then delete it. There's only one way, right?"*
>
> ✅ **Or force it:**
>
> ```bash
> docker rm -f <container-id>       # ✅ no error — stop + remove in one
> ```
>
> *"So I can remove a container forcefully without stopping it — by adding just one flag, `-f`."*

> 😄 She'd "already removed" the container and was baffled. The class debugged it: *"Change the name."* / *"Already existing container."* → correct.

## 6. The Mess That Force-Removing Leaves Behind

> ⚠️ **Her question after using `rm -f`:** *"Do you know the **consequences** of doing this?"*
>
> *"The container is gone because I removed it forcefully. But **my layers are still there**, my content is still there — I'm just not able to see it in `docker ps`. It's still occupying my storage, still occupying my network, still occupying the volume."*

### The two concepts you need names for

| Term | What it is |
|---|---|
| **Dangling image** | *"Sometimes you're using images and after a few days or months they're still there in your laptop and you're not using them — or you modified those images, or they're not needed as of now."* Untagged, orphaned image layers. |
| **Unused container** | A container that's been force-removed or whose image is gone — *"still occupying storage, network and volume"* but invisible in `docker ps`. |
| **Zombie process** | The processes **inside** an unused container: *"this container, we don't have any image, but still processes are running inside it. Still occupying the CPU and memory of my laptop. **The processes, they don't have any master.**"* |

## 9. `docker rmi` — Removing Images, and All The Ways It Fails

### 🎯 "Untagged" then "Deleted" — why two lines?

```bash
docker rmi nginx:latest
# Untagged: nginx:latest
# Deleted: sha256:...
```

> 💡 **First, what that `sha256:...` string is.** It's the image's **digest** — a fingerprint calculated from the image's actual contents. Change one byte and you get a completely different digest.
>
> ```
>  nginx:latest          ← a TAG. A sticky label. Can be moved to a different image tomorrow.
>  nginx@sha256:9b1a…    ← a DIGEST. The content itself. Can never mean anything else.
> ```
>
> ✅ **Which is why Class 1's "you fetch it by a single SHA line" matters:** if you deploy `nginx:latest`, you can't be sure your teammate got the same bytes you did. If you deploy `nginx@sha256:9b1a…`, you both provably have the identical image. That's what "reproducible build" means in practice.

> 🎯 **Her question:** *"Why does it say **untagged** and then **deleted**? It's supposed to say only 'deleted'."*
>
> ✅ **Because a tag and an image are different things.** The tag `nginx:latest` is a *label pointing at* image layers. Docker first **removes the label**, and only then — if nothing else references those layers — deletes the actual data.
>
> 💡 Which is exactly why `docker tag nginx mynginx:v1` from Class 6 doesn't copy anything: two tags, one image.

### The error when a container is using it

```bash
docker run -d --name mynginx1 nginx
docker rmi nginx:latest
```

```
Error response from the daemon: conflict: unable to delete nginx:latest
(must be forced) - image is being used by running container ...
```

> 🎯 **She dwelt on the wording:** *"**Error response from the daemon.** So this is what the daemon means — the daemon is handling everything."*
>
> **Your two options:**
>
> ```bash
> docker stop mynginx1 && docker rmi nginx:latest   # ✅ the polite way
> docker rmi -f nginx:latest                        # ⚡ the forced way
> ```

### 💀 And what forcing it leaves you with

She forced it. Then:

```bash
docker ps -a
```

> ⚠️ *"Container is **still running** — but I can see there is **no name** of the container, there is **no image** for the container. **That is what we call an unused container.** And inside this unused container, there are **zombie processes** — this container doesn't have any image, but processes are still running inside it, still occupying the CPU and memory of my laptop."*

## 12. Dockerfile Instructions — Recap With New Details

She re-walked all the instructions, and three of them got genuinely new material.

### 🆕 `ENV` vs `ARG` — the real difference

| | **`ENV`** | **`ARG`** |
|---|---|---|
| Available at | **run** time (and build time) | **build** time only |
| Set inside the Dockerfile | `ENV NODE_ENV=development` | `ARG NODE_ENV=development` |
| Overridden from the CLI | via `docker run -e` | via **`docker build --build-arg`** |

```bash
docker build --build-arg NODE_ENV=production -t myimage .
#            └──────────────────────────────┘
#               this is ARG's whole reason to exist
```

> ✅ **Her framing:** *"If you want to give an environment-specific variable, use `ENV` inside the Dockerfile. But if you want to apply the **argument** — then when we're doing `docker build -t`, at that time I'll add `--build-arg` and the same argument name."*

### 🆕 `USER` — the security instruction nobody remembers

She exec'd into a container and pointed at the prompt:

```
root@9594518fce35:/#
└─┬─┘
  the DEFAULT user is root
```

```dockerfile
FROM node:24-alpine
...
USER node          # ← add this
CMD ["npm", "start"]
```

> ⚠️ **Why it matters:** *"If we did not specify any user inside the Dockerfile — this is a Node.js application, so we enter `node`. Whenever someone execs inside my container they are **not able to see root**, because root user has all these **sudo privileges**."*
>
> ✅ *"So you should **never, ever** directly run like this. Instead, you need to add `USER` inside your Dockerfile **for security purposes**."*
>
> 💡 **This is "shift left" from Class 1, in one line of a Dockerfile.** A container running as root means a container escape gets root. Adding `USER` costs nothing.

### 🆕 A new detail on `CMD` vs `ENTRYPOINT`

The familiar rule:

| | Overridable? |
|---|---|
| **`CMD`** | ✅ yes |
| **`ENTRYPOINT`** | ❌ no |

**And the new bit she added:**

> 📌 *"When you **stop** a container and **start** it, it will execute the **ENTRYPOINT**. If you **restart** a container, it will execute the **CMD**."*
>
> 🔍 **Worth a note, because this is easy to over-apply:** in practice Docker re-runs the container's *full* configured command (`ENTRYPOINT` + `CMD` together) on both `start` and `restart` — the two aren't split across the two commands. Her point is best held as the thing she said elsewhere and is definitely true: **`ENTRYPOINT` always runs, no matter how the container comes up; `CMD` is the part a `docker run` argument can replace.** For her assessment, give the overridable/not-overridable answer — that's the one being tested.

### `COPY` vs `ADD`, once more

| | **`COPY`** | **`ADD`** |
|---|---|---|
| Local files | ✅ | ✅ |
| URLs / remote files | ❌ | ✅ |
| Auto-extract zip / tar / RPM | ❌ | ✅ |

### The full instruction table

| Instruction | Does |
|---|---|
| `FROM` | base image + tag |
| `WORKDIR` | *"set the working directory inside an image"* |
| `COPY src dst` | local → container |
| `ADD src dst` | COPY + download + auto-extract |
| `RUN` | run a command at **build** time |
| `ENV k=v` | environment variable (run time) |
| `ARG k=v` | build-time argument (`--build-arg`) |
| `EXPOSE port` | declare the port |
| **`USER`** | 🆕 which user the container runs as — **not root** |
| `CMD [...]` | start command — overridable |
| `ENTRYPOINT [...]` | start command — not overridable |

## 13. Multi-Stage Dockerfiles — Today's Main Topic

### 🎯 Why they exist — and a student nailed it instantly

> 🎯 **Her setup:** *"There was a problem: if you're creating a container for a Node.js application, a Java application — one thing is related to **storage**, which you all faced. Right? You all saw 30 GB, 50 GB, 10 GB."*
>
> **Student, immediately:** *"`node_modules`."*
>
> 🎤 *"**Exactly. He understood why we need a multi-stage Dockerfile.**"*

### The problem, precisely

```
npm install
   └─► node_modules/     ←  1 GB? 2 GB? 3 GB?
   └─► build/  or  dist/  or  target/   ←  the ONLY bit production needs
   └─► test/              ←  also not needed in production
```

> 🧠 **Why `node_modules` is so absurdly large — and what you're actually throwing away.**
>
> Your app might depend on 10 packages. But each of those depends on 20 more, and each of *those*… so you end up with thousands of folders. Worse, most of it is **build-time only**: compilers, test frameworks, type definitions, linters. None of it runs in production.
>
> ```
>  SINGLE-STAGE IMAGE                 MULTI-STAGE IMAGE
>  ┌────────────────────────┐         ┌────────────────────┐
>  │ node base       ~50 MB │         │ node base   ~50 MB │
>  │ node_modules   ~800 MB │  ────►  │ prod deps   ~90 MB │
>  │  ├ typescript          │         │ your dist/   ~2 MB │
>  │  ├ jest, eslint        │         └────────────────────┘
>  │  ├ webpack             │            ≈ 140 MB total
>  │  └ …2000 more folders  │
>  │ your source      ~2 MB │
>  └────────────────────────┘
>       ≈ 850 MB total
> ```
>
> ✅ **Three wins from one technique:** the image is ~6× smaller (faster to push, pull and start), your **source code never ships** (only the built output does), and **Trivy has far less to scan** — every dev dependency you drop is one less possible vulnerability.

> ✅ *"We don't want to take all the files and storage — maybe 1, 2, 3 GB. **We can't take that in production.** Those files are not necessary. We just need the **build folder**."*
>
> 💡 **Folder names by ecosystem:** Node → `build/` or `dist/` · Java/Maven → `target/`. *"And sometimes if you're adding test cases then the test folder is already there — that's what I've seen in my organisation."*

### The Dockerfile

```dockerfile
# -------------------------
# Stage 1: Build
# -------------------------
FROM node:24-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .

# -------------------------
# Stage 2: Production
# -------------------------
FROM node:24-alpine AS production
WORKDIR /app
COPY --from=builder /app/package*.json ./
RUN npm install --omit=dev
COPY --from=builder /app/server.js ./
EXPOSE 3000
CMD ["npm", "start"]
```

### ✅ Only TWO things make it multi-stage

> ✅ **She repeated this four times, because it really is the whole trick:**
>
> ```
> 1.  AS builder            ← on the first FROM, names that stage
> 2.  COPY --from=builder   ← in the second stage, pulls files OUT of stage 1
> ```
>
> *"For multi-stage you just need one thing: `AS builder`. Second thing, in the runtime stage: `--from=builder`. **Two things only** to create a multi-stage Dockerfile."*

### Reading it stage by stage

**Stage 1 — builder:**

| Line | What it does |
|---|---|
| `FROM node:24-alpine AS builder` | base image, **named** `builder` |
| `WORKDIR /app` | work inside `/app` |
| `COPY package*.json ./` | bring in the dependency manifest |
| `RUN npm install` | creates the giant `node_modules` inside `/app` |
| `COPY . .` | bring in the source |
| *(and in a real app)* `RUN npm run build` | produces `dist/` |

**Stage 2 — production:** a **completely fresh image**. Nothing from stage 1 exists here unless you explicitly copy it.

| Line | What it does |
|---|---|
| `FROM node:24-alpine AS production` | fresh, empty base |
| `COPY --from=builder /app/package*.json ./` | ⭐ reach back into stage 1 |
| `RUN npm install --omit=dev` | install **production deps only** |
| `COPY --from=builder /app/server.js ./` | ⭐ copy **only** the built output |
| `EXPOSE 3000` | |
| `CMD ["npm", "start"]` | |

> ✅ **The result:** `node_modules` from the build (with all the dev tooling, compilers, test frameworks) **never enters the final image.** You ship the output, not the workshop.

### 💡 Two ways to say "production only"

```dockerfile
RUN npm install --omit=dev       # (older syntax: --only=production)
```

**or**

```dockerfile
ENV NODE_ENV=production
RUN npm install
```

> ✅ *"Previously we added `ENV NODE_ENV=development`. If you want to make it production, you write `--only=production` here. **If you don't want to write it, you can add `ENV NODE_ENV=production` inside your Dockerfile.** If you're not adding it inside your Dockerfile, then you need to add `--only=production`."* Either works — that's the `ENV` from §12 paying off.

### ⚠️ Multi-stage ≠ multi-container

> ⚠️ **She flagged this twice across two classes:** *"**Multi-stage is a different thing, multi-container is a different thing.** Two different topics we need to learn."*
>
> | | Means |
> |---|---|
> | **Multi-stage** | **one** Dockerfile, **one** final image, multiple `FROM` blocks — a *build technique* |
> | **Multi-container** | **many** containers running together — that's **Docker Compose**, Class 9 |

> 💡 **Also possible:** the two stages don't have to use the same base image. *"You can use a different image. There are no constraints — you can use anything else. Just two things: `AS builder` and `--from`."* A classic real-world combo is build with `node`, serve with `nginx`.

### 🧪 The live build (do this yourself)

```bash
git clone https://github.com/Nency-Ravaliya/devops-heros.git
cd devops-heros/session6-7-docker/multi-stage-dockerfile
ls                                          # Dockerfile, package.json, server.js

```

>
> Then open **`localhost:8080`** → *"Hello World from Docker Multi-Stage Build!"* 🎉

## 16. Cheat-Sheet

### Lifecycle

| Command | Does |
|---|---|
| `docker build -t <name> .` | Dockerfile → image |
| **`docker container create --name <n> <img>`** | image → **created** (not started) |
| `docker start <n>` | created/stopped → **running**, from PID 1 |
| **`docker run -d --name <n> -p H:C <img>`** | create **+** start, in one command |
| `docker pause <n>` / `docker unpause <n>` | freeze / unfreeze internal services |
| `docker stop <n>` | graceful shutdown → **exited** |
| **`docker restart <n>`** | resume from the stopped state ⭐ |
| `docker rm <n>` | remove (must be stopped first) |
| **`docker rm -f <n>`** | force-remove a **running** container |
| `docker ps` | **running** only |
| **`docker ps -a`** | **all**, including exited ⭐ |
| `docker logs <n>` | see output from a detached container |

### Images

| Command | Does |
|---|---|
| `docker pull <img>` | download an image |
| `docker images` | list local images |
| **`docker image inspect <img>`** | full JSON — entrypoint, CMD, networking, volumes |
| `docker tag <img> <new:tag>` | add another tag (no copy happens) |
| `docker rmi <img>` | untag **then** delete |
| **`docker rmi -f <img>`** | force, even if a container is using it |

### Inside a container

| Command | Does |
|---|---|
| **`docker exec -it <n> /bin/bash`** | open a shell inside ⭐ |
| `docker exec -it <n> <command>` | run one command inside |
| *(inside)* `pwd` `ls` `cd` `cat` | it's a mini Linux |

### Cleanup

| Command | Removes |
|---|---|
| **`docker system prune`** | ⭐ stopped containers + unused networks + dangling images + build cache |
| `docker container prune` | **stopped** containers only |
| `docker image prune` | dangling images only |
| `docker volume prune` | unused volumes |
| `docker network prune` | unused networks |
| `docker builder prune` | build cache only |
| **`docker system df`** | how much disk Docker is using (run it **before** pruning) |

### Multi-stage

| Keyword | Does |
|---|---|
| **`FROM <img> AS builder`** | name a stage |
| **`COPY --from=builder <src> <dst>`** | pull files out of a named stage |
| `RUN npm install --omit=dev` | production dependencies only |
| `ENV NODE_ENV=production` | the alternative to the flag above |

### Concepts

| Term | Means |
|---|---|
| **Immutable** | image can't change — edit code → **rebuild** |
| **PID 1** | the container's main process; kill it → container dies |
| **Created state** | container exists, PID 1 not started |
| **Paused** | services frozen, container still running |
| **Exited** | stopped gracefully, state saved |
| **Dangling image** | untagged, orphaned image layers |
| **Unused container** | a container with no image — still eating storage |
| **Zombie process** | a process inside an unused container, with no master |
| **`--name`** | name your container, or get `competent_thompson` |
| **Detach mode (`-d`)** | run in the background — *"always, always"* on servers |
| **Container hostname** | 🎯 **the same string as the container ID** |
| **Docker host** | any machine running Docker — including every Kubernetes worker node |
| **`docker blame`** | doesn't exist 🙂 — but **`git blame`** does, and it's how you find who broke the pipeline |
